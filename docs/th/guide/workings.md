# Cap ทำงานอย่างไร {#how-cap-works}

Cap ไม่ได้พยายามตัดสินว่าผู้เข้าชมเป็นมนุษย์หรือไม่ แต่ทำให้ทุกคำขอมีต้นทุนการคำนวณ ซึ่งต่ำสำหรับผู้เข้าชมคนเดียว แต่สูงสำหรับคนที่ส่งคำขอหลายพันครั้ง และตรวจสอบว่าการคำนวณนั้นเกิดขึ้นในเบราว์เซอร์จริง

## สิ่งที่เกิดขึ้นเมื่อมีคำขอ {#what-happens-on-a-request}

1. เมื่อวิดเจ็ตปรากฏ มันจะขอ challenge จากเซิร์ฟเวอร์ของคุณ เซิร์ฟเวอร์จะตอบกลับด้วย token ที่ลงลายเซ็นและอธิบาย challenge นั้น โดยปกติจะมีสคริปต์ instrumentation มาด้วย วิดเจ็ตจะเริ่มรันสคริปต์ใน iframe ที่ถูกแซนด์บ็อกซ์ไว้ทันที
2. เบราว์เซอร์แก้ proof of work ใน Web Workers โดยใช้ WebAssembly การแก้จะเริ่มเมื่อผู้เข้าชมโต้ตอบกับหน้าเป็นครั้งแรกหรือเมื่อคลิกวิดเจ็ต ขึ้นอยู่กับ challenge
3. วิดเจ็ตรวบรวมผล instrumentation แล้วส่งผลลัพธ์ทั้งสองส่วนไปยังเซิร์ฟเวอร์ เซิร์ฟเวอร์ตรวจลายเซ็นของ token และ proof of work ทำเครื่องหมายว่า challenge ถูกนำไปแลกแล้ว จากนั้นจึงตรวจผล instrumentation
4. ถ้าทุกอย่างผ่าน เซิร์ฟเวอร์จะออก token ที่ใช้ได้ครั้งเดียว วิดเจ็ตใส่ token ลงในฟอร์ม และ backend ของคุณตรวจสอบด้วย `/siteverify` ก่อนเชื่อถือข้อมูลที่ส่งมา

เซิร์ฟเวอร์ไม่เก็บสถานะของ challenge ที่ยังเปิดอยู่ เพราะทุกอย่างที่ต้องใช้อยู่ใน token ที่ลงลายเซ็นแล้ว เซิร์ฟเวอร์เก็บเฉพาะ challenge ที่ถูกนำไปแลกแล้วและ token ที่ออกไป

## ทำไมต้อง proof of work {#why-proof-of-work}

CAPTCHA ทุกตัวแก้ได้ในที่สุด ไม่ว่าจะด้วยโมเดลภาพ การทำวิศวกรรมย้อนกลับ หรือคนที่ได้รับค่าจ้างต่อการแก้ สิ่งที่ CAPTCHA ควบคุมได้คือต้นทุนของการแก้แต่ละครั้ง

สมมติว่าผู้ส่งสแปมจ่าย $1 เพื่อส่งข้อความ 10,000 ข้อความ แล้วมีรายได้ $10 จากข้อความเหล่านั้น ถ้า Cap เพิ่มต้นทุนของข้อความเหล่านั้นเป็น $100 การส่งสแปมรอบนั้นก็ขาดทุน ผู้เข้าชมที่กรอกฟอร์มหนึ่งครั้งใช้เวลา CPU ราวครึ่งวินาที และไม่ต้องเห็นปริศนาเลย

แนวคิดนี้มาจาก [Hashcash](https://www.researchgate.net/publication/2482110_Hashcash_-_A_Denial_of_Service_Counter-Measure)

## การตรวจสอบสองชั้น {#the-two-layers}

**Proof of work** แสดงว่าไคลเอนต์ใช้ทรัพยากรในการคำนวณจริง เมื่อใช้ SHA-256 GPU แก้ challenge ต่อวินาทีได้มากกว่า CPU ราว 150 เท่า ทำให้ผู้โจมตีจ่ายเงินเพื่อผ่านการป้องกันได้ในราคาถูก [HashWX](./hashwx.md) ซึ่งเป็นค่าเริ่มต้น ลดความได้เปรียบนี้เหลือราว 2 เท่า

**[Instrumentation](./instrumentation.md)** แสดงว่าการคำนวณเกิดขึ้นในเบราว์เซอร์ แต่ละ challenge มีสคริปต์ที่สร้างขึ้นใหม่และคำนวณเลขผ่าน DOM โดยเซิร์ฟเวอร์รู้คำตอบที่สคริปต์ควรให้ การรันมันนอกเอนจินเบราว์เซอร์จริงทำได้ยาก มันยังตรวจจับเครื่องมืออัตโนมัติและเอเจนต์ AI ที่พบบ่อย รวมถึงให้คะแนนลักษณะการเคลื่อนตัวชี้และการกดแป้นพิมพ์ที่ผู้เข้าชมใช้เข้าถึงวิดเจ็ตได้ด้วย

แต่ละชั้นชดเชยช่องว่างของอีกชั้น proof of work เพียงอย่างเดียวแก้ได้ด้วยสคริปต์ที่ไม่มีเบราว์เซอร์ และ instrumentation เพียงอย่างเดียวแก้จำนวนมากได้ในราคาถูกด้วยเบราว์เซอร์จริงหลายตัว ทั้งสองอย่างหยุดฟาร์มที่จ้างคนแก้ไม่ได้ แต่ proof of work ยังทำให้การแก้แต่ละครั้งของคนเหล่านั้นมีต้นทุน

## ความเป็นส่วนตัว {#privacy}

Cap ไม่ตั้งคุกกี้และไม่เก็บ telemetry ทั้ง challenge, token และสถิติอยู่บนเซิร์ฟเวอร์ของคุณ เมื่อเปิดการให้คะแนนพฤติกรรม วิดเจ็ตจะส่งการเคลื่อนตัวชี้และจังหวะการกดแป้นพิมพ์ของผู้เข้าชมไปยังเซิร์ฟเวอร์ของคุณ แต่ไม่ส่งว่ากดปุ่มใดหรือพิมพ์อะไร วิดเจ็ตเรียก endpoint ที่คุณกำหนด และเรียก jsDelivr เพื่อโหลดไฟล์ WASM เว้นแต่คุณจะ[โฮสต์ไฟล์เอง](./widget.md#self-hosting-the-widget) ดู[การปฏิบัติตามข้อกำหนด](./compliance.md)สำหรับ GDPR, CCPA และการเข้าถึง
