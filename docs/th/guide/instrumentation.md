# challenge แบบ instrumentation {#instrumentation}

challenge แบบ instrumentation ตรวจสอบว่า challenge ถูกแก้ในเบราว์เซอร์จริง โดยทำงานควบคู่กับ proof-of-work เปิดไว้เป็นค่าเริ่มต้นสำหรับคีย์ใหม่ใน capd และต้องเลือกเปิดเองใน[ไลบรารี core](./capjs-core.md#instrumentation)

## หลักการทำงาน {#how-it-works}

ทุก challenge มาพร้อมโปรแกรมที่เซิร์ฟเวอร์ไม่เคยส่งมาก่อน เลขคณิตในโปรแกรมเปลี่ยนทุกครั้ง ตัวแก้จึงต้องอ่านและรันโปรแกรมใหม่ทุกครั้ง แทนที่จะส่งคำตอบเก่าซ้ำ ทุกอย่างที่โปรแกรมจดไว้เกี่ยวกับหน้าจะถูกแฮชรวมเข้าไปในคำตอบ และเซิร์ฟเวอร์คำนวณคำตอบนั้นใหม่ ไคลเอนต์จึงแก้ข้อมูลที่จดไว้ไม่ได้โดยไม่ทำให้การแก้ challenge ล้มเหลว

เฟรมใช้ origin เดียวกับหน้า โปรแกรมจึงเห็นหน้าที่อยู่รอบเฟรมได้ หน้าที่ใช้ Content Security Policy แบบเข้มงวดต้องตั้ง `window.CAP_SCRIPT_NONCE` และ[หน้าที่มีบั๊กการแทรก HTML](./widget.md#pages-with-an-html-injection-bug)แยกเฟรมออกได้ด้วย `CAP_ISOLATE`

## การตรวจจับเบราว์เซอร์อัตโนมัติ {#automated-browser-detection}

เมื่อเปิด **Attempt to block headless browsers** ใน capd หรือ `blockAutomatedBrowsers` ใน core เซิร์ฟเวอร์จะบล็อกเบราว์เซอร์ที่มีร่องรอยของระบบอัตโนมัติ ได้แก่ `navigator.webdriver`, user agent แบบ headless, แพตช์จากปลั๊กอิน stealth, โปรโตคอล Firefox ของ Playwright หรือหน้ากับ Web Worker ที่รายงานข้อมูลอุปกรณ์ไม่ตรงกัน การตรวจสอบมองหาระบบอัตโนมัติและการดัดแปลง ไม่เคยตรวจว่าผู้ใช้เลือกเบราว์เซอร์ใด รายการที่ไม่ผ่านจะอยู่ใน `blockedBy` ส่วนสัญญาณที่อ่อนกว่าจะอยู่ใน `riskFlags` โดยไม่บล็อก

## การตรวจจับการโต้ตอบ {#interaction-detection}

ฟังก์ชันนี้ยังอยู่ในขั้นทดลองและปิดไว้เป็นค่าเริ่มต้น เมื่อเปิด **Block automated clicks and typing** โปรแกรมจะนับการคลิกและการกดปุ่มที่สคริปต์ส่งมาแทนผู้เข้าชม หากพบอย่างใดอย่างหนึ่งครบสามครั้ง การแก้ challenge จะไม่ผ่าน โปรแกรมไม่อ่านค่าในฟิลด์ และไม่สนใจฟิลด์รหัสผ่าน รหัสใช้ครั้งเดียว และบัตรชำระเงิน

## การให้คะแนนพฤติกรรม {#behavior-scoring}

การให้คะแนนพฤติกรรมปิดไว้เป็นค่าเริ่มต้นและตั้งแยกรายคีย์ โปรแกรมบันทึกว่าตัวชี้เคลื่อนมาถึงวิดเจ็ตอย่างไร และจังหวะการกดปุ่ม แต่ไม่บันทึกว่ากดปุ่มใด เซิร์ฟเวอร์แปลงข้อมูลนั้นเป็นคะแนนตั้งแต่ 0 ถึง 1 และผลการตัดสินเป็น `ok`, `suspicious`, `automated` หรือ `agent` และบล็อก `automated` ที่ 0.75 เป็นค่าเริ่มต้น เส้นทางตัวชี้ที่เป็นเส้นตรง การกดที่สคริปต์ส่งมา หรือการพิมพ์ด้วยจังหวะที่สม่ำเสมอเกินจริง ล้วนทำให้คะแนนสูงขึ้น

[โหมดล่องหน](./invisible.md)และ[โหมดลอย](./floating.md)เรียก `solve()` โดยไม่มีการกดที่วิดเจ็ต จึงไม่ผ่านบนคีย์ที่บังคับให้ต้องกด

## การตรวจจับ AI agent {#ai-agent-detection}

Cap ระบุชื่อ AI agent จากร่องรอยที่เครื่องมือของมันทิ้งไว้บนหน้า จากรูปแบบการคลิกและการพิมพ์ และจากเฮดเดอร์ `User-Agent` กับ `Signature-Agent` ที่มีลายเซ็น เมื่อตรวจพบ agent จะเพิ่ม `agent:<name>` ใน `riskFlags` คีย์เลือกได้ว่าจะบล็อก agent ทุกตัว บล็อกเฉพาะตัวที่ระบุได้ด้วยความมั่นใจสูง หรือยอมให้ agent ที่มีลายเซ็น [Web Bot Auth](https://datatracker.ietf.org/doc/draft-meunier-web-bot-auth-architecture/) ที่ตรวจสอบแล้วผ่านไป

## สิ่งที่หยุดไม่ได้ {#what-it-cant-stop}

โปรแกรมรันในเบราว์เซอร์ของผู้เข้าชม การป้องกันจึงมุ่งให้การปลอมมีต้นทุนสูงกว่าการรันจริง ได้แก่ built-in ที่ถูก freeze แฮชที่ครอบคลุมทุกฟิลด์ ผลลัพธ์ที่ผูกกับ challenge เดียว และเครื่องหมายความล้มเหลวที่มีแต่ทำให้ไม่ผ่าน แต่ Cap ยังแยกคนออกจากเบราว์เซอร์จริงที่คนควบคุมอยู่ไม่ได้ จึงหยุดคนที่รับจ้างแก้ challenge, agent ที่ส่งอินพุตมาเป็นเหตุการณ์ปกติของระบบปฏิบัติการ หรือเบราว์เซอร์ที่บิลด์ใหม่จากซอร์สเพื่อซ่อนระบบอัตโนมัติไม่ได้ proof-of-work คือสิ่งที่ยังเก็บต้นทุนจากการแก้แต่ละครั้งเหล่านั้น

รหัสความล้มเหลวอยู่ใน[การแก้ปัญหา](./troubleshooting/instrumentation.md#error-codes)

## วิดเจ็ตจากรุ่นก่อนหน้า {#widgets-from-earlier-releases}

วิดเจ็ตรุ่นเก่ายังแก้ challenge กับเซิร์ฟเวอร์ใหม่ได้ และการแก้เหล่านั้นจะมีแฟล็กความเสี่ยง `legacy_widget` โดยจะไม่ผ่านด้วย `instr_widget_outdated` บนคีย์ที่บล็อกการโต้ตอบอัตโนมัติ ให้คะแนนพฤติกรรม หรือบล็อก agent การอัปเดตวิดเจ็ตจะแก้ปัญหานี้
