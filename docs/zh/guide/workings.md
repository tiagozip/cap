# Cap 是如何工作的

Cap 不尝试判断访客是不是人类。它让每次请求都付出一定的计算成本，对单个访客而言成本很低，但对发送数千次请求的人来说就很高。它还会检查计算是否在真实的浏览器中运行。

## 请求的处理过程

1. 验证组件一旦可见，就会向你的服务端请求质询。服务端返回描述质询的签名令牌，通常还会附上 instrumentation 脚本。验证组件立即在沙箱化的 iframe 中启动该脚本。
2. 浏览器在 Web Workers 中使用 WebAssembly 求解工作量证明。根据质询的类型，求解会在访客首次与页面交互时，或点击验证组件时开始。
3. 验证组件收集 instrumentation 结果，并将两种结果一起发给服务端。服务端检查令牌签名和工作量证明，将质询标记为已兑换，然后检查 instrumentation 结果。
4. 如果全部通过，服务端会签发一次性令牌。验证组件将它放入你的表单，后端则在信任此次提交前通过 `/siteverify` 校验令牌。

服务端不为尚未兑换的质询保存状态，因为所需信息都在签名令牌中。它只存储已兑换的质询和已签发的令牌。

## 为什么使用工作量证明

每一种 CAPTCHA 最终都能被解开，无论是通过图像模型、逆向工程，还是按次付费的人工求解。CAPTCHA 能控制的是每次求解的成本。

假设垃圾信息发送者花费 $1 发送 10,000 条消息，并从中赚取 $10。如果 Cap 将这些消息的成本提高到 $100，这次投放就会亏钱。填写一张表单的访客只需付出约半秒的 CPU 时间，而且不需要看到任何谜题。

这一思路来自 [Hashcash](https://www.researchgate.net/publication/2482110_Hashcash_-_A_Denial_of_Service_Counter-Measure)。

## 两层验证

**工作量证明**表明客户端付出了计算成本。对于 SHA-256，GPU 每秒解出的质询数约为 CPU 的 150 倍，攻击者因此能用很低的成本绕过限制。默认的 [HashWX](./hashwx.md) 将这一优势降到了约 2 倍。

**[Instrumentation](./instrumentation.md)** 表明计算在浏览器中运行。每个质询都带有一个新生成的脚本，通过 DOM 执行算术运算，服务端知道它应该得到的答案。在真实浏览器引擎之外运行它很困难。它还能检测常见的自动化工具和 AI 智能体，并根据访客的指针和键盘输入如何到达验证组件进行评分。

两层验证弥补彼此的不足。仅有工作量证明时，不使用浏览器的脚本也能求解。仅有 instrumentation 时，大量真实浏览器就能以很低的成本完成求解。两者都拦不住人工打码农场，但工作量证明仍然让每次人工求解付出一定成本。

## 隐私

Cap 不设置 cookie，也不收集遥测数据。质询、令牌和统计数据都留在你的服务端。启用行为评分后，验证组件会向你的服务端发送访客的指针移动和按键时序，但绝不发送按下了哪些键或输入了什么内容。验证组件会调用你指定的端点，并从 jsDelivr 获取 WASM 文件，除非你[自行托管这些文件](./widget.md#自行托管验证组件)。GDPR、CCPA 和无障碍访问相关内容见[合规性](./compliance.md)。
