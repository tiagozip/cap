# Cap vs Anubis

Anubis 是一个基于工作量证明的反爬虫工具，在自托管社区很受欢迎，用于在边缘拦截 AI 训练爬虫和激进的抓取程序。它和 Cap 共享工作量证明这个核心，但瞄准的是不同的问题。

## 快速结论

当你想在反向代理层面为整个站点或路径设一道防机器人和爬虫的门槛（通常是因为爬虫在吞噬你的带宽）时，用 **Anubis**。当你想保护某个具体的*操作*（表单提交、API 调用、账号注册），同时让正常浏览不受影响时，用 **Cap**。

## Anubis 合适的场景

- 你想在整个站点或子路径前面立一道 PoW 墙。
- 威胁模型是边缘侧的大规模抓取或机器人驱动的请求洪水。
- 你能接受让每位访客在任何页面加载前都先解一个小质询。

## Cap 更胜一筹的场景

- **按操作防护，而不是按页面浏览防护。** Cap 保护表单、注册、联系页面和 API 端点——正是滥用转化为成本的地方。访客可以正常浏览。
- **难度按操作设置。** Anubis 的质询必须足够小，才不会拖累每次页面加载，这限制了难度的上限。Cap 按操作配置，因此可以在注册或登录表单上把难度调得更高，而不影响浏览体验。
- **两层验证。** Cap 在 PoW 之上叠加了 [instrumentation 质询](../instrumentation.md)，即使机器人用 GPU 加速搞定了工作量证明这一步，仍然需要伪造出一个真实的浏览器环境。
- **带控制台的 Standalone 服务端。** Cap 开箱即带数据分析、多站点密钥管理，以及兼容 reCAPTCHA 的 siteverify 端点。
- **验证组件的用户体验。** Cap 是有意让人类在表单上看得见的：有复选框、进度指示和品牌展示区。Anubis 则是一道透明的关卡。

## 两者可以共存

如果你已经在站点前面运行 Anubis 来防爬虫，你仍然可以在站内那些高价值的表单和 API 端点上使用 Cap。两者解决的是不同的问题，互不冲突。
